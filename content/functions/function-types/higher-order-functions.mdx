# Higher-order Functions

<DocSource docs={["lambdas", "inline-functions"]} />

A higher-order function takes a function as a parameter or returns one. Most of the Kotlin
standard library is higher-order — `map`, `filter`, `fold`, `forEach`, `let`, `use`. The
part worth understanding is `inline`, because it is the difference between a lambda
allocating an object and a lambda disappearing into the call site, and it is what makes a
bare `return` or `continue` legal inside one.

Outputs below come from running `examples/functions/higher-order-functions.kt`.

## Taking a function

`fold` is the canonical example. The `combine` parameter has function type `(R, T) -> R`:

```kotlin
fun <T, R> Collection<T>.myFold(
    initial: R,
    combine: (acc: R, nextElement: T) -> R,
): R {
    var accumulator: R = initial
    for (element: T in this) {
        accumulator = combine(accumulator, element)
    }
    return accumulator
}

val items = listOf(1, 2, 3, 4, 5)
val sum = items.myFold(0) { acc: Int, i: Int ->
    print("acc = $acc, i = $i, ")
    val result = acc + i
    println("result = $result")
    result
}
println(sum)
```

```text
acc = 0, i = 1, result = 1
acc = 1, i = 2, result = 3
acc = 3, i = 3, result = 6
acc = 6, i = 4, result = 10
acc = 10, i = 5, result = 15
15
```

The lambda's parameter types are usually inferable, and a function reference works wherever
a lambda does:

```kotlin
println(items.myFold("Elements:") { acc, i -> acc + " " + i })
println(items.myFold(1, Int::times))
```

```text
Elements: 1 2 3 4 5
120
```

## Returning a function

A function returning a function type is how you build a configured operation once and reuse
it:

```kotlin
fun applyTwice(x: Int, f: (Int) -> Int): Int = f(f(x))
fun multiplierOf(factor: Int): (Int) -> Int = { it * factor }

println(applyTwice(5) { it + 3 })
val triple = multiplierOf(3)
println(triple(7))
println(multiplierOf(10)(7))
println(items.map(multiplierOf(2)))
```

```text
11
21
70
[2, 4, 6, 8, 10]
```

`multiplierOf(10)(7)` is two calls: the first returns a function, the second invokes it.

## What inline actually does

Each function value is an object that captures a closure, so a higher-order function costs
an allocation and a virtual call per lambda. `inline` copies the function's body — and the
lambda's body — into the call site instead. You can see it in a stack trace:

```kotlin
fun notInlined(block: () -> Unit) { block() }
inline fun inlined(block: () -> Unit) { block() }

fun whereAmI(label: String) {
    val frame = Thread.currentThread().stackTrace[2]
    println("$label -> ${frame.className.substringAfterLast('.')}.${frame.methodName}")
}

notInlined { whereAmI("non-inline") }
inlined { whereAmI("inline") }
```

```text
non-inline -> Higher_order_functionsKt.main$lambda$3
inline -> Higher_order_functionsKt.main
```

The non-inline lambda has its own synthetic method, `main$lambda$3`; the inline one has no
frame of its own at all — its body was compiled directly into `main`.

<Callout type="warning">
  `inline` makes the generated code bigger at every call site, so it pays off for small
  functions wrapping a lambda and costs you for large ones. An inline function with no
  function-typed parameters and no `reified` type parameters draws a warning saying so:

  ```text
  warning: expected performance impact from inlining is insignificant.
  Inlining works best for functions with parameters of function types.
  ```

  That warning is the signal you reached for `inline` out of habit.
</Callout>

### noinline

An inlined lambda has no object — its body was pasted into the call site — so there is
nothing to store or hand on. The rule is: **inlinable lambdas can only be called inside the
inline function, or passed as an inlinable argument to another inline function.** Anything
else needs `noinline`, and a `noinline` lambda can then be manipulated freely, including
being stored in a field:

```kotlin
@PublishedApi
internal var stored: (() -> Unit)? = null

inline fun storeOne(inlined: () -> Unit, noinline notInlined: () -> Unit) {
    inlined()
    stored = notInlined   // only legal because of `noinline`
}

storeOne({ println("  inlined body runs immediately") }, { println("  stored body runs later") })
println("  stored is null? ${stored == null}")
stored?.invoke()
```

```text
  inlined body runs immediately
  stored is null? false
  stored body runs later
```

Both lambdas were written at the same call site; only the `noinline` one still existed
afterwards.

### crossinline

Use `crossinline` when the inline function calls the lambda from **another context** — inside
an object expression or a nested function. That forbids non-local returns from it, which is
precisely what the other context cannot support.

<Callout type="info">
  `@Suppress("NOTHING_TO_INLINE")` silences the "insignificant impact" warning when you are
  sure the inlining is wanted anyway.
</Callout>

## Non-local return

Because the body is copied in, a bare `return` inside a lambda passed to an inline function
can leave the *enclosing* function:

```kotlin
fun firstNegativeOrNull(ints: List<Int>): Int? {
    ints.forEach {
        if (it < 0) return it // non-local return, out of firstNegativeOrNull
    }
    return null
}

println(firstNegativeOrNull(listOf(1, 2, -3, 4)))
println(firstNegativeOrNull(listOf(1, 2, 3)))
```

```text
-3
null
```

`break` and `continue` work for the same reason, including from inside a lambda that an
inline function invokes within a loop:

```kotlin
fun sumNonNull(values: List<Int?>): Int {
    var total = 0
    for (value in values) {
        val n = value ?: run {
            println("  skipping null")
            continue
        }
        total += n
    }
    return total
}

println(sumNonNull(listOf(1, null, 2, null, 3)))
```

```text
  skipping null
  skipping null
6
```

A `continue` inside a `run { }` block — legal only because `run` is inline and the loop
encloses it.

<Callout type="info">
  The same `return` in a lambda passed to a **non-inline** function is a compile error, not
  a local return — `error: 'return' is prohibited here.` A lambda cannot make its caller
  return. The fix is a label, `return@forEach`, covered under
  [return](/functions/standard-functions/return).
</Callout>

## Reified type parameters

Inlining also means the type argument is known at the call site, so an inline function can
declare `reified T` and then use `T` as if it were a real class — `is T`, `as T`,
`T::class` — with no `Class<T>` parameter and no reflection:

```kotlin
inline fun <reified T> countOf(items: List<Any>): Int = items.count { it is T }
inline fun <reified T> typeNameOf(): String = T::class.simpleName ?: "?"

val mixed = listOf(1, "two", 3.0, "four", 5)
println(countOf<String>(mixed))
println(countOf<Int>(mixed))
println(typeNameOf<StringBuilder>())
```

```text
2
2
StringBuilder
```

`reified` is only available on `inline` functions — a normal function has no call site to
substitute the type into. A type with no runtime representation, such as `Nothing` or a
non-reified type parameter, cannot be passed for a `reified` parameter.

## Inline properties

`inline` also works on **property accessors** — but only those with no
[backing field](/classes-and-objects/class-members/properties). Annotate one accessor, or
the whole property to inline both:

```kotlin
class Config(@PublishedApi internal val raw: Map<String, String>) {
    inline val isEmpty: Boolean get() = size == 0   // whole property

    val size: Int
        inline get() = raw.size                     // one accessor
}

val config = Config(mapOf("a" to "1", "b" to "2"))
println(config.size)
println(config.isEmpty)
println(Config(emptyMap()).isEmpty)
```

```text
2
false
true
```

At the call site an inline accessor is inlined exactly like an inline function.

<Callout type="warning">
  A property with a backing field cannot be inlined at all. This:

  ```kotlin
  var bar: String = "x"
      inline set(v) { field = v }
  ```

  fails with:

  ```text
  error: inline property cannot have a backing field.
  ```

  The reason is the same as everywhere else on this page: inlining pastes the accessor body
  into the caller, and `field` only exists inside the class.
</Callout>

## Public API inline functions

An inline function that is `public` or `protected`, and not inside a `private` or
`internal` declaration, is part of the module's **public API**. Other modules call it *and
inline it at their own call sites* — which means its body is baked into their compiled
output.

That creates a binary-compatibility risk: change the body, and any module that is not
recompiled keeps running the old one. To contain it, Kotlin forbids public-API inline
functions from touching **non-public-API declarations** — anything `private` or `internal`:

```kotlin
private val secret = 42
inline fun leak(): Int = secret
```

```text
error: public-API inline function cannot access non-public-API property.
```

The escape hatch is `@PublishedApi`, which marks an `internal` declaration as usable from
public-API inline code — the `Config` and `stored` examples above both need it:

```kotlin
@PublishedApi
internal var stored: (() -> Unit)? = null
```

<Callout type="info">
  `@PublishedApi` is a promise, not a loophole. The declaration is now effectively public
  for compatibility purposes — changing it can break callers that have already inlined it —
  and when an `internal` **inline** function is marked `@PublishedApi`, its body is checked
  as if it were public too.
</Callout>
