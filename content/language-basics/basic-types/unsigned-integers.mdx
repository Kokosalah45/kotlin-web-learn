# Unsigned Integers

<DocSource docs={["unsigned-integer-types"]} api={["kotlin-stdlib/kotlin/-u-int/"]} />

Four unsigned types that use the whole bit range for non-negative values. They are
[inline classes](/classes-and-objects/more-on-classes-and-objects/inline-class) wrapping
their signed counterparts, not primitives, and they are **not** related to the signed types
by subtyping in either direction. Their intended use is bit patterns and native interop —
not "a number that cannot be negative".

Outputs below come from running `examples/language-basics/unsigned-integers.kt`.

## The four types

```kotlin
println("UByte  ${UByte.SIZE_BITS} bits: ${UByte.MIN_VALUE}..${UByte.MAX_VALUE}")
println("UShort ${UShort.SIZE_BITS} bits: ${UShort.MIN_VALUE}..${UShort.MAX_VALUE}")
println("UInt   ${UInt.SIZE_BITS} bits: ${UInt.MIN_VALUE}..${UInt.MAX_VALUE}")
println("ULong  ${ULong.SIZE_BITS} bits: ${ULong.MIN_VALUE}..${ULong.MAX_VALUE}")
```

```text
UByte  8 bits: 0..255
UShort 16 bits: 0..65535
UInt   32 bits: 0..4294967295
ULong  64 bits: 0..18446744073709551615
```

Same widths as the signed types, the sign bit spent on magnitude instead.

## Literals

`u` or `U` means unsigned; `uL` / `UL` pins it to `ULong`. With an expected type, the
literal adopts it; without one, the compiler picks `UInt` or `ULong` by size:

```kotlin
val b: UByte = 1u
val s: UShort = 1u
val l: ULong = 1u
val a1 = 42u
val a2 = 0xFFFF_FFFF_FFFFu
val a3 = 1UL
```

```text
1 UByte
1 UShort
1 ULong
42 UInt
281474976710655 ULong
1 ULong
```

Note `val a3 = 1UL` is a `ULong` even though `1` fits comfortably in `UInt` — the suffix
wins.

## The point: the full bit range

A 32-bit `AARRGGBB` colour does not fit in a signed `Int` as a positive number:

```kotlin
data class Color(val representation: UInt)

val yellow = Color(0xFFCC00CCu)
println(yellow)
println(yellow.representation)
println(0xFFCC00CCu.toInt())
```

```text
Color(representation=4291559628)
4291559628
-3407668
```

Same 32 bits, read as `4291559628` unsigned and `-3407668` signed. `UByteArray` likewise
lets you write `ubyteArrayOf(0xEFu, 0xBBu, 0xBFu)` without a `toByte()` on every element.

## Arithmetic wraps at zero

```kotlin
val zero: UInt = 0u
println(zero - 1u)
println(UInt.MAX_VALUE + 1u)
println(1u - 2u)
println(3u / 2u)
println(3u % 2u)
```

```text
4294967295
0
4294967295
1
1
```

<Callout type="warning">
  `0u - 1u` is `4294967295`, not `-1` and not an error. Subtraction between unsigned values
  cannot produce a negative result, so an expression like `a - b` where `b` might exceed `a`
  silently becomes a huge number — far worse than a negative one, because it still passes a
  `>= 0` check. Compare before subtracting, or do the arithmetic signed.
</Callout>

## Converting

There is no implicit conversion in either direction; `toUInt()`, `toInt()`, `toUByte()`
and friends reinterpret the bits:

```kotlin
val signed: Int = -1
println(signed.toUInt())
println(signed.toUInt().toInt())
println(255u.toByte())
println((255u).toUByte())
println(UInt.MAX_VALUE.toLong())
println(ULong.MAX_VALUE.toLong())
println((-1).toUInt() == UInt.MAX_VALUE)
```

```text
4294967295
-1
-1
255
4294967295
-1
true
```

Two things worth pulling out. `255u.toByte()` is `-1` — narrowing to a **signed** byte
reinterprets the top bit. And `UInt.MAX_VALUE.toLong()` is correct (`4294967295`) because
`Long` is wide enough, while `ULong.MAX_VALUE.toLong()` is `-1` because it is not.

## Ranges

`UInt` and `ULong` have ranges and progressions, and those are stable API:

```kotlin
println((1u..5u).toList())
println((1u..10u step 3).toList())
println(5u in 1u..10u)
println((1u..5u)::class.simpleName)
```

```text
[1, 2, 3, 4, 5]
[1, 4, 7, 10]
true
UIntRange
```

## Stability and opt-in

The types, their ranges and their progressions are stable. **Unsigned arrays** —
`UByteArray`, `UShortArray`, `UIntArray`, `ULongArray` — are Beta and need opt-in:

```kotlin
@OptIn(ExperimentalUnsignedTypes::class)
fun byteOrderMark(): UByteArray = ubyteArrayOf(0xEFu, 0xBBu, 0xBFu)

println(byteOrderMark().joinToString { it.toString(16) })
```

```text
ef, bb, bf
```

Without the annotation you get a warning that the feature is not stable. Whether to make
your own callers opt in is a judgement call — but remember a Beta API can change
incompatibly.

## What they are at runtime

```kotlin
println(42u::class.qualifiedName)
println(42u::class.java.isPrimitive)
```

```text
kotlin.UInt
false
```

<Callout type="info">
  An unsigned type is an inline class, so in most places it compiles down to the underlying
  signed primitive with no wrapper object — but it is not itself a primitive type, and it
  **does** box in the same situations a nullable or generic value does. Treat it as cheap,
  not free.
</Callout>

## When not to use them

The official docs are explicit that unsigned types are the wrong tool for "a quantity that
should not be negative" — a collection size or an index. Two reasons:

- Signed integers let you detect mistakes. `List.lastIndex` is `-1` for an empty list,
  which is a usable sentinel; the unsigned equivalent would wrap to a huge number.
- Unsigned is not a restricted signed. The ranges only partly overlap and neither type is a
  subtype of the other, so every boundary becomes a conversion.

Use them for bit patterns, fixed-width binary formats, hashes, and native APIs whose
signatures are unsigned.
